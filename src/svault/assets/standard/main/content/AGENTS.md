# 科研主库 Agent 规则

使用中文与用户交流。本文件约束主库及其下属项目；项目自己的 AGENTS.md 只能补充项目要求，不能放宽主库边界。

## 开始任务前的必读与定位
1. 先读 `规则与模板/科研库规则.md`，确认用户最新要求和实际目录；不要假定初始化时的结构仍然有效。
2. 涉及具体项目时，先定位该叶级 Vault，读取其 `AGENTS.md`、项目主页和 `项目.json`（旧项目无此文件时以主页属性为准）。检查项目编号、目录、已有记录及拟写入位置。
3. 新建项目时先读 `规则与模板/新建项目.md` 和 `规则与模板/项目文件夹模板/项目文件夹模板说明.md`，使用标准目录蓝图和新建工具；不得重新运行主库初始化来修复项目。
4. 规则、项目身份或来源无法确定时，暂停依赖这些信息的写入并说明缺失内容；能够独立完成的只读检查可以继续。

## 库结构
本目录是主 Vault。`科研项目` 下允许普通分类文件夹；每个独立研究目标对应一个项目子 Vault。
项目子库是叶级 Vault，内部禁止再建 Vault。以项目 `.obsidian`、`AGENTS.md` 和项目主页识别边界。
主库维护总览、规则、模板、共享知识。项目笔记与实验记录写入对应项目子库。
`规则与模板/项目文件夹模板/标准科研项目/template.json` 是项目文件夹模板的权威清单；笔记模板只负责单篇笔记。不得把模板蓝图打开成 Vault 或当成真实研究数据。
子库目录名（Obsidian 注册名）与项目编号都必须全局唯一；编号创建后保持稳定。分类可以是多层普通文件夹，但不得穿过已有项目 Vault。

## 写入路由与最小修改
- 跨项目知识写入 `共享知识`，项目只记录应用、复现与具体结论，并通过 URI 引用共享知识原件。
- 项目记录按项目 AGENTS 的目录路由写入；临时未分类内容写入当前库收件箱。
- 先检查目标是否已有记录；追加到正确记录或新增唯一名称，不覆盖用户调整，不批量重命名或迁移既有项目。
- 新笔记必须填写正确的 `type`、`project_id`、`status`、`created`。实验、结果和交接另填其对应身份及来源属性；不能把未替换的模板占位符写进正式记录。
- Bases 从实际笔记属性生成视图，不手工伪造数据库行，不将模板或示例当作真实实验成果。

## 内容与证据
文献、实验配置、日志、结果表、关键图表及外部物料位置属于笔记资产。
实验代码、原始数据集和模型权重存放在库外。本阶段不开发 SEBer 或外部仓库关联工具。
禁止编造文献、指标和研究结论；明确区分事实、解释与假设，证据不足标记待核实。
允许新增记录、更新索引与进展；已有结论仅追加证据和修订说明，替换原结论须用户确认。
交接暂用人工方式；保留原始材料，以 Markdown 日志属性支持 Bases 索引。
实验结果必须关联可定位的证据，写明已知的代码、数据版本/划分、配置与评估条件；未知项标记待核实。人工交接只有在整理产出可定位且未核实事项已记录后才能标记 complete。

## 配置与链接
库内 Wiki 链接采用全局唯一笔记名，避免父子库解析同名笔记不同。跨库使用 Obsidian URI。
共享知识只保存一份。Bases 是当前 Vault 内文件属性的视图，不是外部数据库。
只有主库启用 fast-note-sync，子库禁止独立同步。凭据只放插件本地配置，不写说明、模板、日志或 Git。
新建项目使用 `工具/svault.exe project create`，创建后同步更新主库的子库配置目录清单。Vault 内不保留 Python 脚本或兼容入口。
跨设备对子库配置的同步依赖每台设备登记额外目录。共享清单为 `规则与模板/子库同步目录.json`，本机用 `工具/svault.exe sync apply` 应用；不得通过复制含密钥的插件 data.json 配置第二设备。
禁止自动批量清理附件、删除交接原件或覆盖已有项目目录。
插件运行时索引和设备布局由本机维护，不能将它们的存在误判为故障。不得输出凭据或将凭据复制进项目模板、交接记录、子库或测试目录。

## 完成标准
1. 核对写入位置、属性、项目身份、证据、Wiki/URI 链接和叶级 Vault 边界；按改动范围运行相应检查。
2. 修改库内容、规则或结构模板后运行 `工具/svault.exe blueprint validate` 和 `工具/svault.exe check`。CLI 源码及完整 exe 测试在独立 Git 仓库进行，测试只用临时目录，不把 Python 测试脚本放回 Vault。
3. 报告实际新增/修改内容、检查结果和未验证事项。插件已配置不等于已联网同步；不宣称未运行的实验、多端测试或构建已经通过。

## 统一 CLI 操作规范
1. 维护前阅读 `规则与模板/Vault管理CLI使用说明.md`；在本主库目录执行 `工具/svault.exe whoami` 和 `rules` 确认上下文。用 `permissions` 或 `operations` 查看可用操作。
2. 可由 CLI 完成的新增、删除、属性修改、查询、模板与 Agent 规则维护，优先用 CLI。普通命令不能访问隐藏配置、工具、身份文件或原始交接材料；不要用其他文件工具绕过子库权限。
3. 主库 Agent 管理项目创建/整体回收/恢复、全库模板与规则、共享知识、同步目录；用 `--project 编号` 选择项目。子库 Agent 只处理本项目笔记、状态、本库补充规则、回收站和历史，共享知识只读。
4. 删除默认移动到 `.trash`，禁止永久删除。修改前查询 SHA256；正文优先追加，全文替换必须已有明确用户授权并声明 `--authorized-replace`。不得把该开关当成授权来源。
5. 主库 AGENTS 模板位于 `规则与模板/Agent模板/主库AGENTS.md.template`；项目模板仍为目录蓝图中的 `AGENTS.md.template`。先 render 预览，再 apply；项目补充写入 `AGENTS.local.md`，生成时保留并合并。
6. 不手工修改 `维护日志` 或 `.trash/svault` 的恢复记录。依据返回的操作编号查历史、恢复或回滚；不能把其他端的日志可见性当作恢复数据已备份的证据。
7. 改动 CLI 源码在独立仓库开发，Vault 仅部署 `工具/svault.exe`。CLI 维护工具不属于 SEBer 或实验仓库交接开发，不扩大到该范围。
8. 版本用 `version` 或 `--version` 查询；升级先 `update check`，再由主库执行 `update apply`，命令退出后用 `update status` 核实覆盖结果。保留旧版备份，不把 pending 状态当作已成功。

## v1.1.0 结构维护
先读取 vault.json 和项目元数据。init 用于空目标；已有库用 doctor/repair，repair 默认预览，应用必须核对计划哈希。个人配置只从明确选择的本地源库继承，不复制插件 data.json。不得以修复名义替换现有笔记、规则或配置。
